# Дизайн-система

Как устроены две параллельные темы проекта и через какие CSS-грабли уже
прошли на практике. Все значения токенов и все примеры кода в этом файле
взяты напрямую из текущего `src/index.css` и `src/components/teacher/
theme-ui.jsx`/`src/components/glass-dialog.jsx` — не из истории
обсуждений (палитры в этом проекте менялись несколько раз, старые
значения в документацию не попадают).

---

## 1. Две темы — общая картина

### Где определены токены

Всё в одном файле — `src/index.css`. Общая структура:

- `@theme inline { ... }` (строки 7–58) — маппинг CSS-переменных на
  Tailwind v4 (`--color-primary: var(--primary)` и т.д.), общий для обеих
  тем: сами Tailwind-утилиты (`bg-primary`, `text-foreground`, …) читают
  переменные, а не хардкодят цвет, поэтому одна и та же утилита даёт
  разный цвет в зависимости от того, внутри `.teacher-theme` она
  оказалась или нет.
- `:root { ... }` (строки 73–121) — токены **ученической** темы (тёплая,
  янтарная).
- `.teacher-theme { ... }` внутри `@layer base` (строки 345–392) —
  токены **учительской** темы (розовая), переопределяющие те же
  переменные только для потомков этого класса.

### Как физически разделены темы

Не отдельные CSS-файлы и не переключение класса на `<html>`/`<body>` —
**скоуп через shadowing одних и тех же CSS custom properties**.
`.teacher-theme` навешен на корневой `<div>` `TeacherDashboard.jsx`
(`<div className="teacher-theme relative min-h-screen ...">`) — все
компоненты внутри (весь `components/teacher/*`) читают `var(--primary)`
и получают розовое значение, а всё, что рендерится вне этого div
(студенческая сторона, публичные экраны), видит корневые `:root`-токены
и остаётся янтарным. Никакого рантайм-переключателя темы нет — какая
тема применится, решает исключительно то, в каком поддереве DOM
оказался компонент.

### Актуальная палитра (сверено с кодом)

|---|---|---|
| `--background` | `oklch(0.955 0.014 70)` — тёплый почти-белый | `oklch(0.975 0.012 350)` — розовый почти-белый |
| `--primary` | `oklch(0.72 0.19 47)` — янтарно-оранжевый | `oklch(0.66 0.185 5)` — розовый |
| `--radius` | `1.75rem` | `1.5rem` |
| `--card` | `oklch(1 0 0 / 42%)` (полупрозрачная) | `oklch(0.995 0.008 350 / 55%)` (полупрозрачная) |
| `--destructive` | `oklch(0.62 0.19 22)` | `oklch(0.6 0.2 20)` |
| Акцентный градиент | `--gradient-warm: linear-gradient(135deg, oklch(0.78 0.17 55), oklch(0.68 0.2 38))` | `--gradient-orb: radial-gradient(circle at 32% 28%, oklch(0.84 0.15 350), oklch(0.62 0.2 8))` |
| Доп. токены только этой темы | `--card-opaque` (для 3 экранов без декоративного фона — см. `docs/FRONTEND_MAP.md`) | `--rose-deep`/`--rose-soft` (акцентный текст), `--balance-ok`/`--balance-warn`/`--balance-danger` (баланс в «Финансы»), `--glass`/`--glass-strong`/`--glass-border` (см. §2) |

`--gradient-page` определён в `.teacher-theme` (строки 377–384), но **нигде не используется** ни одним компонентом (проверено `grep` по `src/`) — реальный фон страницы учителя задаётся отдельным правилом `body:has(.teacher-theme)` (см. §3, грабля про порядок отрисовки), не этой переменной. Мёртвый токен, не заметка из старого обсуждения — оставлен как есть, ни на что не влияет.

**Тёмная тема отключена целиком**, не удалена — весь блок `.dark {...}` и
`@media (prefers-color-scheme: dark) {...}` (строки 123–220) обёрнут в
`/* ... */` с явным комментарием-объяснением прямо в коде: `.dark`
никогда не навешивается никаким JS в приложении, а автоматическое
`prefers-color-scheme` перебивало тщательно подобранную тёплую светлую
палитру нечитаемым сочетанием. Компоненты, которые пишут
`dark:bg-...`/`dark:text-...` (например `student-tags.jsx`, см. §2), это
наследие того же решения — классы валидны и ничего не ломают, просто
сейчас гарантированно никогда не активируются.

### Шрифты

Подключены как Google Fonts в `index.html` (`<link
href="https://fonts.googleapis.com/css2?family=Manrope:...&family=Unbounded:...">`),
замаплены в переменные в `@theme inline`:

- `--font-sans: 'Manrope', ...` → Tailwind `font-sans` — основной текст
  тела, применяется глобально (`body { @apply font-sans }`).
- `--font-display: 'Unbounded', ...` → Tailwind `font-display` —
  заголовки/акцентные числа, применяется **точечно**, руками на каждом
  заголовке (`<h1 className="font-display ...">` и т.п.) — глобального
  `h1,h2,h3{font-family:var(--font-display)}` в проекте нет (в отличие
  от исходных мокапов, откуда мигрировали обе темы), поэтому при
  добавлении нового заголовка `font-display` нужно проставлять явно,
  иначе он молча съедет на `Manrope`.

Оба шрифта общие для обеих тем — визуальное разделение тем идёт только
через цветовые токены, не через типографику.

## 2. Компоненты и утилиты

### Стеклянные утилиты — у каждой темы свой набор имён (специально не унифицированы)

**Ученическая** (`glass`/`glass-soft`/`glass-inset`, все три — прозрачный
белый поверх декоративного фона):

| Утилита | Непрозрачность фона | Когда использовать |
|---|---|---|
| `glass` | 30% белого (самая прозрачная) | Крупные контейнеры поверх декоративного фона (карточка входа, обёртки диалогов) |
| `glass-soft` | 43% белого | Карточки контента внутри страницы (история уроков и т.п.) |
| `glass-inset` | 28% белого, без `backdrop-filter` в отдельном блюре (тень другая) | Вложенные «утопленные» элементы — ячейки PIN-кода, плашки внутри карточки |

Все три используют общий `--glass-blur: saturate(160%) blur(28px)`.

**Учительская** (`glass-panel`/`glass-tile`, читают токены `--glass`/
`--glass-strong`/`--glass-border`, которые определены **только** внутри
`.teacher-theme` — использование этих утилит вне скоупа темы даст
`undefined`-переменные и невидимый фон):

| Утилита | Непрозрачность (`--glass*`) | Когда использовать |
|---|---|---|
| `glass-panel` | 30% (`--glass`), блюр 18px | Крупные секции-панели (`Panel` в `theme-ui.jsx`) |
| `glass-tile` | 42% (`--glass-strong`), блюр 12px, чуть плотнее | Мелкие элементы внутри панели — кнопки (`GhostBtn`), инпуты, строки списков |

Обе темы также используют декоративный шумовой слой поверх фона, но
разными утилитами: студенческая — `grain` (текстура на самом элементе,
через `::after`), учительская — `bg-grain-blobs`/`blob-a`/`blob-b`/
`grain-layer` (фиксированный слой из двух размытых пятен + шум,
`z-index: -10`, см. §3 про грабли с порядком отрисовки).

### Переиспользуемые обёртки модалок/поповеров

**`GlassDialog`/`GlassDialogContent`/`GlassDialogTitle`/
`GlassDialogDescription`** (`src/components/glass-dialog.jsx`) — только
для студенческой стороны. Тонкая обёртка над `components/ui/dialog.jsx`
(shadcn/Base UI): `GlassDialog` — это буквально реэкспорт `Dialog` без
изменений, вся стилизация — в `GlassDialogContent` (`rounded-4xl
border-white/50 bg-white/50 backdrop-blur-2xl` + `shadow-glass`). Как
пользоваться в новом коде:

```jsx
<GlassDialog open={open} onOpenChange={setOpen}>
  <GlassDialogContent>
    <GlassDialogTitle>Заголовок</GlassDialogTitle>
    <GlassDialogDescription>Подзаголовок</GlassDialogDescription>
    {/* содержимое */}
  </GlassDialogContent>
</GlassDialog>
```

**`TeacherDialog`/`TeacherDialogContent`/`TeacherDialogTitle`/
`TeacherDialogDescription`** (`theme-ui.jsx`) — учительский эквивалент,
но построен напрямую на `@base-ui/react/dialog`, не на shadcn-обёртке.
Ключевая особенность — проп `elevated`:

```jsx
<TeacherDialog open={open} onOpenChange={setOpen}>
  <TeacherDialogContent>          {/* обычный диалог */}
  <TeacherDialogContent elevated>  {/* диалог поверх уже открытого TeacherDialog */}
    <TeacherDialogTitle>...</TeacherDialogTitle>
    ...
  </TeacherDialogContent>
</TeacherDialog>
```

`elevated` **обязателен**, если диалог открывается из контрола, который
сам уже находится внутри другого открытого `TeacherDialog` (пример в
коде — «Сбросить подключение» бота внутри диалога уведомлений). Без него
диалог не просто окажется не на том слое по z-index — он **вообще не
получит фон-подложку** (см. §3, грабля про Base UI и вложенные диалоги).

**`TeacherPopover`/`TeacherPopoverTrigger`/`TeacherPopoverContent`**
(`theme-ui.jsx`) — не модалка, лёгкий поповер без затемнения фона,
«прилипает» к триггеру (`@base-ui/react/popover`). Использовать для
точечного редактирования одного поля рядом с кнопкой (пример — ссылка
для связи с учеником), не для полноценных форм — для тех есть
`TeacherDialog`.

Отдельная, **намеренно не унифицированная** с `TeacherStatusBadge**

не забытая рассинхронизация, если понадобится третий подобный компонент
где-то ещё, стоит решить осознанно, а не механически переиспользовать
один из двух существующих.

## 3. Известные технические грабли

### Приоритет `@layer` в Tailwind v4

**Проблема**: модалки учительской панели (карточка урока, перенос,
отмена, редактор учебных планов, уведомления) открывались вообще без
видимого содержимого и без затемнения фона.

**Причина**: CSS-правило вне любого `@layer` **всегда** перебивает любое
правило внутри именованного слоя — независимо от порядка объявления
слоёв или порядка в файле. `.teacher-theme` изначально был обычным,
неслоёным правилом, объявляющим собственные `background`/`color`; Tailwind
v4 кладёт вывод директивы `@utility` (то есть все Tailwind-утилиты,
включая `glass-panel`/`glass-tile` и обычные `bg-ink/25`) в `@layer
utilities`. На любом элементе, у которого одновременно был класс
`teacher-theme` и утилита, трогающая `background`/`color`
(именно такое сочетание — на портализированном `Backdrop`/`Popup`,
см. следующую грабли), неслоёное правило `.teacher-theme` побеждало
всегда, вне зависимости от порядка классов в `className`.

**Решение**: `.teacher-theme` обёрнут в `@layer base` — тот же слой, что
используют базовые правила самого Tailwind, поэтому утилиты из `@layer
utilities` теперь корректно его перебивают. Видно прямо в
`index.css` (строки 345 и 392 — открывающая/закрывающая `@layer base {`).

### CSS-переменные и React Portal

**Проблема**: те же модалки — после исправления `@layer`-проблемы всё
ещё не получали розовую палитру, показывались с токенами студенческой
темы или вовсе без стилей.

**Причина**: `.teacher-theme`-переопределения CSS-переменных работают
через каскад/наследование по DOM-дереву — но `DialogPrimitive.Portal`/
`PopoverPrimitive.Portal` (Base UI) физически выносят `Backdrop`/`Popup`
из поддерева `.teacher-theme` прямо в `document.body`. Без класса
`teacher-theme` непосредственно на портализированном элементе
переменные `var(--primary)` и т.д. резолвятся в корневые (студенческие)
значения — сам факт, что диалог логически «внутри» учительской панели в
React-дереве, ничего не даёт для CSS-каскада по реальному DOM.

**Решение**: класс `teacher-theme` навешен явно и на `Backdrop`, и на
`Popup` в каждой обёртке — видно в `theme-ui.jsx`:
`className="teacher-theme fixed inset-0 bg-ink/25 ..."` (Backdrop,
`TeacherDialogContent`) и `className="teacher-theme glass-panel fixed
..."` (Popup, там же и в `TeacherPopoverContent`). Правило на будущее:
любой новый портализированный элемент, которому нужны переменные
`.teacher-theme`, обязан нести класс сам, не полагаться на React-родство.

### `position: fixed`/`z-index: auto` и порядок отрисовки

**Проблема**: после починки предыдущих двух багов модалки заработали, но
при попытке добиться точного совпадения фона учительской панели с
макетом декоративный слой пятен (`bg-grain-blobs`) либо не был виден,
либо перекрывался фоновым градиентом.

**Причина**: у позиционированного (`position: relative`) элемента с
`z-index: auto` собственный фон красится на «stack level 0» — **после**
того, как отрисовались его собственные потомки с отрицательным
`z-index`, в рамках того же контекста наложения. `.teacher-theme` —
именно такой элемент (`position: relative`, без явного `z-index`) и
одновременно прямой родитель декоративного слоя (`position: fixed;
z-index: -10`). Если фоновый градиент повесить прямо на `.teacher-theme`,
он рисуется поверх пятен, а не под ними.

**Решение**: градиент вынесен на настоящий `<body>`, через
`body:has(.teacher-theme) { background: linear-gradient(...); }` —
`<body>` не является позиционированным родителем фиксированного слоя, поэтому
конкурировать за порядок отрисовки с ним не может в принципе. Ровно
описано в комментарии над правилом, `index.css` строки 253–263. Общее
правило на будущее (сформулировано там же): **фон, который должен быть
позади `position: fixed`-декоративного слоя, обязан жить на предке,
который не является прямым позиционированным родителем этого слоя.**

### `position: fixed` и `containing block` предков (общий риск, не зафиксированный как реальный баг в этом проекте)

Классическая CSS-ловушка, о которой стоит знать при работе с любым
`position: fixed`-модалом (обе `TeacherDialogContent` и
`GlassDialogContent` центрируются именно так): `transform`, `filter`,
`backdrop-filter` или `will-change` на **предке** превращают этот предок
в containing block для потомков с `position: fixed` — вместо viewport'а
модалка начинает позиционироваться относительно этого предка и
перестаёт быть по-настоящему зафиксированной/отцентрированной на экране.
В этом проекте это не зафиксировано как случившийся баг (оба Base UI
`Dialog.Portal`/`Popover.Portal` рендерят прямо в `document.body`, минуя
любых трансформированных предков, так что риск сейчас не реализован) —
но если когда-нибудь понадобится обернуть часть страницы в контейнер с
`transform`/`filter`/`backdrop-filter` (например, ради анимации перехода
между экранами), и в нём случайно окажется точка рендера портала —
центрирование сломается без единой ошибки в консоли. Держать в уме,
особенно если Portal-таргет когда-нибудь изменят с `document.body` на
что-то внутри дерева страницы.

### Порядок фокуса при открытии — гонка с позиционированием Popover

**Проблема**: попап оплаты в «Финансы» (`AddPaymentForm` внутри
Popover) при открытии дёргал всю страницу к самому верху.

**Причина**: нативный атрибут `autoFocus` на инпуте вызывает
синхронный `.focus()` прямо во время начального коммита React — **до**
того, как Base UI/floating-ui успели асинхронно (через `rAF`/layout
effect) вычислить финальную позицию `Positioner`. В момент вызова
`.focus()` элемент физически ещё стоит на позиции по умолчанию (около
верха документа), а голый `.focus()` по умолчанию скроллит элемент во
вьюпорт — отсюда прыжок к верху страницы за миг до того, как поповер
сам встанет на нужное место.

**Решение**: атрибут `autoFocus` убран из инпута (`add-payment-form.jsx`)
— подтверждено, в текущем коде его больше нет. У самих `TeacherDialogContent`/
`TeacherPopoverContent` есть **свой** механизм начального фокуса
(`initialFocus={popupRef}`, см. следующий абзац) — он таймингом привязан
к уже вычисленной позиции, в отличие от голого `autoFocus`, поэтому
конфликта с ним нет, только с *дублирующим* нативным атрибутом поверх
него.

Отдельно, тот же `initialFocus={popupRef}` в `TeacherDialogContent`
(`theme-ui.jsx`, комментарий там же) решает смежный, но другой баг:
Base UI по умолчанию фокусирует первый доступный для табуляции элемент
внутри диалога голым `.focus()` **без** `preventScroll: true` — только
фокус самого контейнера попапа получает эту защиту
(`FloatingFocusManager`: `preventScroll: elToFocus ===
floatingFocusElement`). Передача `initialFocus={popupRef}` форсирует
именно этот, защищённый от скролла путь для каждого учительского
диалога разом, вместо того чтобы пытаться откатывать прыжок постфактум.

### Base UI и вложенные диалоги — `Dialog.Backdrop` не рендерится по умолчанию

**Проблема**: диалог подтверждения «Сбросить подключение» (бот учителя),
открытый из поповера внутри уже открытого диалога уведомлений, показывал
попап вообще без затемнения/блюра фона — не проблема z-index, элемент
физически отсутствовал в DOM.

**Причина**: у Base UI `Dialog.Backdrop` (собственный исходник пакета,
`node_modules/@base-ui/react/dialog/backdrop/DialogBackdrop.js`) — `enabled:
forceRender || !nested`. «Вложенным» (`nested`) Base UI автоматически
считает `Dialog.Root`, открытый пока есть уже открытый предок-`Dialog.Root`
(через React-контекст, не что-то, во что явно включаешься) — и в этом
случае **не рендерит свой Backdrop вообще**, предполагая, что затемнения
внешнего диалога достаточно.

**Решение**: проп `elevated` на `TeacherDialogContent` передаёт
`forceRender={elevated}` в `Backdrop` (плюс поднимает z-index, см. §2) —
оба действия обязательны вместе, поднятие одного z-index без
`forceRender` ничего не даст, если элемент не отрисовался. Само это
поведение Base UI и цитата из его исходника — прямо в комментарии над
`Backdrop` в `theme-ui.jsx`.

### Popover на одном z-index с Dialog Backdrop

**Проблема**: поповер, открытый из строки внутри уже открытого диалога
(статус подключения бота в диалоге уведомлений), визуально оказывался
позади попапа этого диалога.

**Причина**: `TeacherPopoverContent`'s `Positioner` изначально был
`z-[100]` — тот же уровень, что и `TeacherDialogContent`'s `Backdrop`,
но **ниже**, чем его `Popup` (`z-[101]`). Поповер и диалог — независимые
компоненты без общего механизма стекинга между собой, в отличие от
вложенных диалогов из предыдущего пункта.

**Решение**: `Positioner` поднят до `z-[110]` — выше любого обычного
`TeacherDialogContent`, поповер теперь всегда поверх диалога, из
которого был открыт.
