# Логика ботов

Устройство Telegram- и VK-ботов как конечного автомата. Основано на
фактическом коде `functions/adapters/telegram.js`,
`functions/adapters/vk.js` и того, что они вызывают из `functions/core/`
(`registration.js`, `lessons.js`, `teacherConnect.js`, `botMessages.js`,
`schedule.js`). Не пересказ кода построчно — контракт поведения.

---

## 1. Общая архитектура

**Разделение ответственности**: вся бизнес-логика (регистрация, уроки,
перенос/отмена, домашка, привязка учителя) живёт в `functions/core/*.js`
и ничего не знает о том, из какого мессенджера пришёл вызов. Адаптеры
(`functions/adapters/telegram.js`, `functions/adapters/vk.js`) —
намеренно тонкий слой: разбирают формат конкретного API в общие
параметры (`studentId`, `lessonId`, дата и т.д.), вызывают одну и ту же
core-функцию, форматируют ответ через `botMessages.js`. Пример: нажатие
кнопки «Подтвердить» в Telegram и в VK в итоге вызывают один и тот же
`confirmReschedule(studentId, lessonId, role)` из `core/lessons.js` —
адаптер только вытаскивает `studentId`/`lessonId` каждый по-своему
(Telegram — резолвом по `chatId`, VK callback — прямо из payload кнопки).

Обратный эффект той же архитектуры: когда предложение переноса/отмены
разрешается (через сайт **или** через нажатие кнопки в любом из ботов),
удаление использованного бот-сообщения с кнопками (`proposalMessage`/
`teacherProposalMessage` на документе урока, см. `docs/DATA_MODEL.md`)
происходит **внутри** `core/lessons.js`, один раз, а не отдельно в каждом
адаптере — поэтому кросс-канальная синхронизация (ответили на сайте —
сообщение в боте пропало) работает без специального кода в адаптерах.

**Где хранится состояние диалога**. Пошаговые сценарии (регистрация,
запрос даты переноса) — это конечный автомат поверх одного документа на
пользователя:

- Telegram: `telegramSessions/{chatId}`
- VK: `vkSessions/{peerId}`

Обе коллекции идентичны по форме (см. `docs/DATA_MODEL.md`): `{ token?,
step, name?, lessonId? }`. Документ **создаётся** при входе в
многошаговый сценарий (`/start <token>`, `/start signup`, ввод токена
регистрации текстом в VK, запрос «перенести урок») и **удаляется** сразу
по завершении шага, для которого он был создан — либо успешно
(`sessionRef.delete()` после `completeRegistration`/`proposeReschedule`),
либо при ошибке (тоже удаляется, чтобы не залипал в сломанном шаге —
пользователь начинает заново). Никакого TTL/cron-очистки нет: документ
либо живёт ровно между двумя сообщениями пользователя, либо не создаётся
вовсе (однократные действия вроде нажатия inline-кнопки сессию не трогают
вообще).

## 2. Входные точки

### 2.1. Регистрация по токену от учителя

- **Telegram**: диплинк `https://t.me/<бот>?start=<token>` — Telegram сам
  превращает переход по ссылке в сообщение `/start <token>`, это надёжно
  (в отличие от VK, см. ниже).
- **VK**: диплинка в привычном смысле нет. Учитель делится ссылкой вида
  `vk.me/<группа>?ref=<token>` **или** голым кодом `<token>` для ручного
  ввода первым сообщением. `ref` VK передаёт в `message.ref` — адаптер
  сначала смотрит туда, и только если `ref` пуст — берёт текст самого
  сообщения как токен (`handleNoSessionMessage`). Оба пути ведут в одну и
  ту же проверку `getRegistrationTokenStatus(token)`.

### 2.2. Самостоятельная регистрация (self-service)

- **Telegram**: точный текст `/start signup` — токен создаётся на лету
  (`createSelfServiceToken`, `isSelfService: true`, без имени наперёд),
  дальше та же машина состояний, что и у обычной регистрации.
- **VK**: точное совпадение текста `"регистрация"` (не подстрока —
  `isSignupRequestText` сравнивает строго, чтобы случайное упоминание
  слова в другом сообщении не сработало как триггер). Тот же
  `createSelfServiceToken()` под капотом.

### 2.3. Подключение репетитора (учителя) к боту

- **Telegram**: `/start teacher_{token}` — префикс `teacher_` проверяется
  в `handleStart` первым, до всех остальных веток, поэтому неоднозначности
  с обычным токеном регистрации нет в принципе.
- **VK**: диплинков с префиксом нет — код (обычный `teacherConnectTokens`
  токен как есть, без префикса) отправляется репетитором себе в сообщения
  сообщества вручную. Отличить его от токена регистрации ученика по
  формату **нельзя** (оба — случайные строки из одного генератора) — VK
  сначала пробует токен как токен регистрации ученика
  (`getRegistrationTokenStatus`), и только если это не он — явным
  Firestore-запросом проверяет `teacherConnectTokens` (`resolveTeacherConnectToken`).
  Порядок проверок: сначала «перенести урок» / «регистрация» по тексту,
  затем токен регистрации ученика, и только в последнюю очередь —
  токен подключения учителя.

### 2.4. Написал без контекста (fallback)

- И в Telegram (`/start` без аргумента), и в VK (текст, не совпавший ни
  с одним из вышеперечисленного) — `WELCOME_NO_TOKEN()`: нейтральное
  приветствие с просьбой попросить у репетитора ссылку. Никакой сессии
  не создаётся.

## 3. Машина состояний регистрации

Общая для обеих платформ (адаптеры реализуют её параллельно, с одними и
теми же шагами `step`). `chatId`/`peerId` ниже — это ключ документа
сессии.

| Текущее состояние | Вход | Что происходит | Следующее состояние |
|---|---|---|---|
| нет сессии | `/start <token>` (TG) или диплинк/ref/текст-токен (VK) | Проверка `getRegistrationTokenStatus`: если `status !== "pending"` → `INVALID_TOKEN()`, сессия не создаётся | нет сессии (ошибка) **или** `awaiting_name` |
| нет сессии | `/start signup` (TG) / точный текст «регистрация» (VK) | `createSelfServiceToken()`, сессия создаётся сразу с этим токеном | `awaiting_name` |
| нет сессии | `/start teacher_{token}` (TG) / произвольный текст, не подошедший под токен ученика (VK) | `resolveTeacherConnectToken` — не создаёт сессию вообще, это одношаговое действие (см. §2.3) | нет сессии (одношаговое действие завершено) |
| `awaiting_name` | любой текст | Текст берётся как имя как есть (без валидации формата), пишется в сессию, `NAME_SAVED(name)` | `awaiting_pin` |
| `awaiting_pin` | текст, не 4 цифры | `INVALID_PIN()`, сессия не меняется | `awaiting_pin` (повтор) |
| `awaiting_pin` | ровно 4 цифры | `completeRegistration(token, name, pin, {platform, id: chatId/peerId})` — создаёт `students/{id}` (см. `docs/DATA_MODEL.md`), помечает токен `used`. Сессия удаляется **в любом случае** (успех или ошибка) | нет сессии |
| `awaiting_pin`, ошибка `completeRegistration` | — | Текст ошибки из `HttpsError`, либо `REGISTRATION_FAILED()` как fallback | нет сессии |

Успешное завершение шлёт `PIN_SAVED(url, showMenuButtonHint)` — ссылку на
личный кабинет; `showMenuButtonHint` (подсказка про кнопку меню внизу
чата) передаётся `true` только в Telegram, у VK такого UI-концепта нет.

Отдельная, параллельная мини-машина состояний — **запрос переноса
текстом** (не через кнопку): `нет сессии` → пользователь пишет «перенести
урок»/«хочу перенести» (`isRescheduleRequestText`, подстрокой, без
токена, только для уже привязанного `chatId`/`peerId`) → бот находит
ближайший `status: "upcoming"` урок, создаёт сессию `{step:
"awaiting_reschedule_date", lessonId}` → следующее сообщение
парсится как дата (`parseRescheduleDateInput`, формат `ДД.ММ ЧЧ:ММ`); при
неудачном парсинге — `RESCHEDULE_INVALID_DATE()`, сессия остаётся в том
же состоянии; при успехе — `proposeReschedule(..., "student")`, сессия
удаляется.

## 4. Обработка вне регистрации

### 4.1. Фото/файл (домашнее задание)

Общий путь в обеих платформах: `extractIncomingFile`/`extractIncomingAttachment`
→ скачать байты (`downloadTelegramFile` по `file_id` / `downloadFileFromUrl`
по прямому URL вложения VK) → `uploadHomeworkFile` (Storage) →
`recordHomeworkSubmission(studentId, url)`.

Привязка к уроку — **не к тому, что открыто на сайте**, а к
`getNearestUpcomingLesson` (с фолбэком на `ensureUpcomingLesson`, если
вообще ничего нет) — так домашка правильно попадает и на внеплановый
(`isExtraLesson`) урок, если он ближе обычного слота. Если привязать
вообще не к чему (`lessonId === null`) — адаптер сам шлёт
`HOMEWORK_NO_LESSON()`; если урок нашёлся, `recordHomeworkSubmission`
уже сам отправил `HOMEWORK_RECEIVED()` через `createNotification`, второй
раз адаптер ничего не шлёт.

Если `chatId`/`peerId` вообще не привязан ни к одному ученику —
`STUDENT_NOT_LINKED()`, файл не скачивается.

### 4.2. Нажатие inline-кнопок (подтверждение/отклонение)

Технически устроено **по-разному** на двух платформах:

- **Telegram**: `callback_query` в теле обновления (`update.callback_query`),
  обрабатывается `handleCallbackQuery`. Данные кнопки — строка `data`
  (например `confirm_reschedule_<lessonId>` или, для учительских кнопок,
  `t_confirm_resch_<lessonId>_<studentId>`). Каждое нажатие **обязано**
  быть подтверждено вызовом `answerCallbackQuery` (иначе кнопка у
  пользователя бесконечно крутит спиннер загрузки) — вызывается всегда, в
  том числе для нераспознанных `data`.
- **VK**: два независимых события. Старые «текстовые» клавиатуры (до
  введения callback-кнопок) шлют обычное `message_new` с `payload` в
  самом сообщении — их разбирает `handleReschedulePayload` (оставлено
  ради уже отправленных старых предложений, не для новых). Актуальные
  клавиатуры — `type: "callback"` — приходят отдельным событием
  `message_event`, не `message_new`; `payload` там уже готовый объект
  (или JSON-строка, парсится `parseVkPayload`) с `action`, `studentId`,
  `lessonId` прямо внутри — резолвить личность по `peerId` не нужно.
  Каждый `message_event` **обязан** завершаться вызовом
  `sendMessageEventAnswer` (иначе VK будет повторно доставлять то же
  нажатие) — вызывается в `handleCallbackEvent` в любом случае, даже если
  `payload`/`peerId` некорректны.

И там, и там есть отдельная ветка для **учительских** кнопок (`t_*` в
Telegram, `teacher_*` в VK payload) — они приходят, когда предложение
исходило от ученика и клавиатуру получил репетитор; резолвятся напрямую
по `studentId`/`lessonId` из данных кнопки, без похода в `telegramSessions`/
привязку `peerId`→студент (у чата репетитора нет такой привязки в
принципе).

### 4.3. Любой другой текст

- Если есть активная сессия (`telegramSessions`/`vkSessions`) —
  обрабатывается её текущим `step` (см. §3).
- Если сессии нет и текст не совпал ни с одним триггером (перенос,
  self-service, токен) — `UNKNOWN_MESSAGE()`.
- То же самое, если сессия существует, но у неё незнакомый `step` (в
  теории недостижимо при нормальной работе кода, но обработано —
  `logger.warn` + `UNKNOWN_MESSAGE()`).

## 5. Исходящие сообщения

Каталог, не тексты — точные формулировки см. `functions/core/botMessages.js`
(единственный источник правды, оба адаптера туда обращаются, своих
текстов не хранят).

| Функция | Когда отправляется |
|---|---|
| `WELCOME_NO_TOKEN` | `/start` без токена (TG) / нераспознанный текст без сессии (VK) |
| `WELCOME_WITH_TOKEN` | Токен регистрации (обычной или self-service) принят, начало анкеты |
| `NAME_SAVED` | Имя записано, запрошен PIN |
| `PIN_SAVED` | Регистрация завершена — ссылка на личный кабинет |
| `INVALID_PIN` | Введён не 4-значный код |
| `INVALID_TOKEN` | Токен регистрации не найден / уже использован |
| `REGISTRATION_FAILED` | `completeRegistration` упал не с `HttpsError` (fallback-текст) |
| `TEACHER_CONNECTED` | Токен подключения репетитора успешно погашен |
| `TEACHER_CONNECT_INVALID` | Токен подключения репетитора не найден/просрочен/чужая платформа |
| `HOMEWORK_RECEIVED` | Домашка принята и привязана к уроку (шлётся из `recordHomeworkSubmission`, не из адаптера) |
| `HOMEWORK_NO_LESSON` | Домашка получена, но привязать не к чему |
| `HOMEWORK_SAVE_FAILED` | Ошибка скачивания/загрузки файла домашки |
| `STUDENT_NOT_LINKED` | `chatId`/`peerId` не привязан ни к одному ученику |
| `UNKNOWN_MESSAGE` | Fallback на нераспознанное сообщение |
| `RESCHEDULE_ASK_DATE` | Начат текстовый запрос переноса — просьба назвать дату |
| `RESCHEDULE_INVALID_DATE` | Дата не распозналась при вводе |
| `RESCHEDULE_REQUEST_SENT` | Запрос переноса от ученика успешно создан |
| `RESCHEDULE_NO_UPCOMING_LESSON` | У ученика нет урока, который можно перенести |
| `RESCHEDULE_CALLBACK_FAILED` | Ошибка при подтверждении/отклонении/предложении переноса |
| `RESCHEDULE_PROPOSED_TO_STUDENT` / `_TO_TEACHER` | Уведомление о новом предложении переноса (с клавиатурой, если получатель — сторона, которая должна ответить) |
| `RESCHEDULE_CONFIRMED` / `RESCHEDULE_REJECTED` | Итог рассмотрения предложения переноса |
| `CANCELLATION_PROPOSED_TO_STUDENT` / `_TO_TEACHER` | Новое предложение отмены (двусторонний флоу) |
| `CANCELLATION_CONFIRMED` / `CANCELLATION_REJECTED` | Итог рассмотрения предложения отмены |
| `LESSON_CANCELLED_BY_TEACHER` | Односторонняя отмена учителем (`cancelLessonDirectly`) — объявление, не предложение |
| `CANCELLATION_CALLBACK_FAILED` | Ошибка при подтверждении/отклонении/предложении отмены |
| `EXTRA_LESSON_ASSIGNED` | Учитель назначил внеплановый урок |
| `ASSIGNMENT_ADDED` / `ASSIGNMENT_UPDATED` | Учитель добавил/изменил текст задания |
| `ASSIGNMENT_FILES_ADDED` / `MATERIAL_ADDED` | К уроку прикреплены файлы |
| `HOMEWORK_SUBMITTED_TO_TEACHER` | Учителю — ученик прислал домашку |
| `REMINDER_MIDDAY_SUMMARY` | Ежедневное сводное напоминание (9:00 МСК) |
| `buildPreLessonMessage` | Часовое напоминание («урок через N часов/минут») |
| `buildTenMinuteReminderMessage` | 5-минутный планировщик, урок начинается совсем скоро |

`RESCHEDULE_KEYBOARDS`/`CANCELLATION_KEYBOARDS` (ученику) и
`RESCHEDULE_KEYBOARDS_FOR_TEACHER`/`CANCELLATION_KEYBOARDS_FOR_TEACHER`
(учителю) — не тексты сообщений, а билдеры inline-клавиатур под каждую
платформу; прикладываются к соответствующим `_PROPOSED_*` сообщениям.

## 6. Известные особенности платформ

- **VK-диплинки ненадёжны, обходятся через ключевые слова/ref/текст.** У
  VK нет аналога `/start <arg>` — `vk.me/<группа>?ref=<token>` передаёт
  `ref` не всегда предсказуемо, поэтому `handleNoSessionMessage` в любом
  случае готов принять токен и просто как голый текст первого сообщения
  (`hasRef ? ref.trim() : text.trim()`). Self-service регистрация в VK —
  это вообще не диплинк, а точное совпадение слова «регистрация».
- **`message_new` обязан быстро получить в ответ строго `"ok"`, иначе VK
  повторно доставит то же событие.** На практике полная обработка (особенно
  скачивание фото + загрузка в Storage) может занимать 3–12 секунд —
  дольше, чем VK готов ждать без ретрая. Без защиты это давало 2–3
  дублирующихся отправки домашки на одно фото. Защита —
  `vkProcessedMessages/{peerId}_{conversationMessageId}`, атомарный
  `.create()` (не `.set()`): если документ уже существует, `.create()`
  бросает исключение с `error.code === 6`, обработка тихо пропускается.
  У этой коллекции нет TTL — растёт неограниченно (см. `docs/DATA_MODEL.md`).
- **`message_new` и `message_event` — разные типы событий VK, с разной
  обязательной «квитанцией».** `message_new` — обычное входящее сообщение
  (текст, вложение, старая текстовая кнопка), отвечать надо строкой `"ok"`
  на весь HTTP-запрос. `message_event` — нажатие callback-кнопки,
  отдельный тип события; кроме ответа `"ok"` на HTTP-запрос, для него
  **дополнительно обязателен** отдельный API-вызов
  `messages.sendMessageEventAnswer` — без него VK продолжает считать
  кнопку «висящей» и будет повторно слать то же нажатие.
- **Telegram `callback_query` требует `answerCallbackQuery`, иначе кнопка
  бесконечно показывает спиннер загрузки** на устройстве пользователя —
  не влияет на повторную доставку (в отличие от VK), но UI выглядит
  сломанным, если забыть вызвать.
- **И `telegramWebhook`, и `vkWebhook` сначала полностью обрабатывают
  событие и только потом отвечают** (`await handleUpdate(...)` /
  `await handleEvent(...)` до `res.status(200).send(...)`) — намеренно,
  чтобы заморозка инстанса Cloud Run сразу после ответа не оборвала ещё
  не завершённую запись в Firestore или отправку ответного сообщения.
  Оба мессенджера терпимо относятся к ответу веб-хука в течение
  нескольких секунд.
- **Telegram `deleteMessage` не сработает для сообщений старше ~48
  часов** (ограничение самого Bot API); VK `messages.delete` с
  `delete_for_all: 1` аналогично ограничено ~24 часами. Оба адаптера
  оборачивают удаление в try/catch и логируют `warn`, не бросая исключение
  — просроченное/уже удалённое сообщение-предложение не должно ронять
  основной флоу подтверждения/отклонения (см. §1 про кросс-канальную
  синхронизацию).
- **У Telegram-фото никогда нет `mime_type`** (`PhotoSize` его не
  передаёт вообще) — Telegram всегда перекодирует фото в JPEG на своей
  стороне, поэтому адаптер просто жёстко подставляет `"image/jpeg"`.
  VK-вложения по типу `doc` тоже не дают MIME напрямую, только
  расширение файла — маппится через собственную таблицу
  `EXTENSION_MIME_TYPES` с фолбэком `application/octet-stream`.
- **VK `messages.delete` принимает именно `message_ids` (обычный id
  сообщения из ответа `messages.send`), не `conversation_message_id`** —
  это два разных идентификатора в API VK, перепутать легко.
